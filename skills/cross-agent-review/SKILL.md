# Cross-Agent Review

## Requirements

- Orca 앱의 `orca` CLI(`orca terminal list|read|send`)로 같은 워크트리의 다른 에이전트 터미널에 메시지를 보낼 수 있어야 한다. Orca가 없으면 같은 원칙(별도 세션 검증 → 근거 직접 확인 → 항목별 판정)을 다른 세션 전달 수단으로 대신하되, 콜백 명령은 그 수단에 맞게 바꾼다.

## Overview

다른 에이전트 세션에 검증을 맡기고, **그 결과를 그대로 믿지 않고 직접 확인한 뒤**, 수용과 반박을 항목별로 사용자에게 보고한다.

**핵심 원리: 검증자의 결론이 아니라 검증자의 근거를 검증한다.**

두 에이전트가 서로 동의하는 것은 품질의 증거가 아니다. 서로 **틀린 곳을 찾아내는 것**이 증거다.

## When to Use

- 한 에이전트가 혼자 내린 결론을 검토받아야 할 때 — 스택 선택, 설계 초안, 조사 결과
- 같은 Orca 워크트리에 다른 에이전트 터미널이 열려 있을 때
- 사용자가 "교차검증", "핑퐁", "다른 에이전트에게 물어봐"라고 할 때

**쓰지 말 것:** 단순 작업 위임(→ `orca-cli` 핸드오프), 사용자가 정해야 할 정책 결정, 한 명이 답을 아는 사실 확인

## Quick Reference

| 단계 | 명령·행동 |
| --- | --- |
| 상대 찾기 | `orca terminal list --worktree active --json` → `agentIdentity` 확인 |
| 내 핸들 확인 | 같은 목록에서 내 터미널 핸들. **콜백 지시에 필요하다** |
| 상태 확인 | `orca terminal read --terminal <handle> --json` |
| 보내기 | `orca terminal send --terminal <handle> --text "..." --enter --json` |
| 긴 내용 | 파일로 쓰고 경로만 전달 |

요청 문안은 `references/request-template.md`를 쓴다.

## 요청에 반드시 넣을 일곱 가지

하나라도 빠지면 왕복이 낭비된다.

1. **콜백 명령을 통째로** — 상대 에이전트는 끝내고도 알리지 않는다. 실행할 명령을 그대로 적어준다
2. **무비판적 동의 금지** — "동의하지 않으면 근거를 들어 반박하라"
3. **확인 실패를 명시하라** — 추정을 사실처럼 쓰지 말 것
4. **출처 URL** — 공식 문서를 직접 열어 확인할 것
5. **저장소 수정 금지** — 검증 단계에서는 문서·코드·의존성을 건드리지 않는다
6. **결과 파일 경로 지정** — 왕복 산출물은 `/tmp`, 결론은 저장소
7. **사용자 결정 항목은 확정 금지** — 정책 판단을 에이전트가 대신 닫지 않는다

## 받은 뒤 — 가장 중요한 규칙

> **직접 확인할 수 있는 주장은 반드시 직접 확인한다.**

상대가 저장소를 근거로 무언가 주장하면 **그 파일을 연다.** 공식 문서를 인용하면 **그 URL을 연다.** 이 규칙 하나가 실제로 다음을 잡아냈다.

- "275개 통과 테스트가 자산이다" → 열어보니 그중 40%가 폐기 도메인 결합
- "Reanimated가 이미 있다" → 패키지만 있고 애니메이션 코드는 RN `Animated` 사용

**확인하지 않고 수용하면 두 에이전트가 같은 오해를 공유하게 된다.** 그게 이 스킬이 막으려는 실패다.

## 항목별 판정

받은 내용을 항목마다 넷 중 하나로 판정하고 **근거를 붙인다.**

| 판정 | 의미 |
| --- | --- |
| **수용** | 상대가 맞고 내가 틀렸다. 무엇이 틀렸는지 명시한다 |
| **부분 수용** | 방향은 맞고 범위나 정도가 과하다 |
| **반박** | 내가 확인한 근거로 상대가 틀렸다 |
| **확인 실패** | 양쪽 다 모른다. 실측 대상으로 넘긴다 |

**내가 틀린 것을 숨기지 않는다.** 철회는 명확히 쓴다.

## 회차 상한

**2회에서 멈춘다.** 요청 → 검증 → 반박 → 재반박이면 충분하다. 3회차부터는 새 정보가 아니라 말이 길어진다.

수렴하지 않으면 그것은 **실측이 필요하다는 신호**다. 논쟁을 계속하지 말고 측정으로 넘긴다.

## 사용자 보고 형식

항목별로 넷을 분리한다.

1. **수용한 것** — 내가 틀린 것을 먼저, 무엇이 왜 틀렸는지
2. **반박한 것** — 근거와 함께
3. **수렴한 결론**
4. **남은 것** — 미확인 항목과 사용자 결정 항목을 구분

결론만 보고하지 않는다. **양쪽이 무엇을 틀렸는지가 사용자가 판단할 재료다.**

### 라벨을 풀어 쓴다

에이전트끼리는 `A`·`B`·`C`, `D-1`, `W-3`, `V-8` 같은 라벨이 효율적이다. **사용자에게는 해독 부담이다.**

- 사용자 보고에서는 **매번 실체를 함께 적는다** — `B` 가 아니라 `Supabase(앱이 DB를 직접 읽고 권한은 SQL로 판정)`
- 라벨이 셋을 넘으면 **표로 먼저 실체를 정의**하고 시작한다
- 사용자가 "그게 뭐였지"를 되묻게 만들면 이미 실패한 것이다

**대화가 길어질수록 위험이 커진다.** 초반에 한 번 정의한 라벨을 수십 턴 뒤에도 그대로 쓰면, 사용자는 그 정의를 기억하고 있지 않다.

## Common Mistakes

| 실수 | 결과 |
| --- | --- |
| 콜백 지시를 빼먹음 | 사용자가 수동으로 상태를 확인해야 함 |
| 상대 결과를 확인 없이 수용 | 같은 오해가 두 에이전트에 고착 |
| 결론만 보고 | 사용자가 판단 근거를 잃음 |
| **라벨만 쓰고 실체를 안 적음** | **사용자가 매번 매핑을 기억해야 함. 대화가 길수록 악화** |
| 3회차 이상 지속 | 새 정보 없이 비용만 증가 |
| 검증 중 저장소 수정 | 무엇이 검증 대상이었는지 사라짐 |
| 정책 결정을 에이전트가 확정 | 사용자 권한 침해 |

## Red Flags — 멈추고 다시 볼 것

- 상대 의견에 **전부 동의**하고 있다 → 직접 확인을 안 했을 가능성
- 상대가 **전부 동의**해 왔다 → 무비판적 동의 금지가 요청에 빠졌을 가능성
- 저장소를 근거로 든 주장을 **파일을 안 열고** 받아들였다
- "대략", "절반", "훨씬"처럼 **측정하지 않은 수치**를 쓰고 있다
- 3회차를 시작하려 한다
- 보고에 **`A`·`B`·`C`나 `W-3` 같은 라벨이 실체 없이** 등장한다
