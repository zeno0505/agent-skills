# 목업 ↔ 화면 스크린샷 대조

승인된 목업과 실제 구현 화면을 **같은 상태·같은 폭의 캡처 쌍**으로 나란히 놓고 차이를 찾는다.
찾은 차이는 하나도 빠짐없이 분류하고, 에이전트가 스스로 풀 수 있는 것은 고치고, 애매한 것만 개발자에게 묻는다.

## 왜 스크린샷인가

디자인 검증은 디자인 도구의 구조화 데이터(노드 트리·스타일 JSON)를 코드와 교차하는 방식이 토큰이 싸고
스크립트로 정확하다. 그 방식을 버리라는 뜻이 아니다. 다만 **화면 수가 적고(대략 상태 10개 안팎)** 모델이
이미지를 충분히 읽을 수 있으면, 캡처 쌍 비교가 더 빨리 "사람 눈에 보이는 차이"를 잡는다.
화면 규모와 모델 비용을 보고 고른다. 화면이 수십 개를 넘으면 구조화 교차나 픽셀 회귀로 돌아간다.

## 기준과 경계

- **목업이 기준이다**(사용자가 다르게 정하지 않는 한). 앱이 목업과 다르면 앱을 의심한다.
- 단, **목업 전용 장치는 가져오지 않는다**: 설계 주석·안내 띠, 화면 ID 표기, 「목업 상태 바꾸기」 같은 데모 조작,
  예시 데이터·예시 근거, 임시 브랜드·로고 자리, 목업에서만 동작하는 점프 링크 등.
- 색·간격은 **앱의 기존 디자인 토큰**으로 맞춘다. 목업 값을 새 하드코딩 색으로 박지 않는다. 토큰에 같은 값이 없으면 질문 대상이다.
- 공용 컴포넌트·전역 스타일 때문에 생긴 차이는 **지역적으로** 고치거나 남은 차이로 기록한다. 전역 규칙을 바꾸면 다른 화면이 깨진다.
- 이 스킬은 대조·분류·수정 제안까지가 기본이다. 실제 수정은 사용자가 맡긴 범위(태스크) 안에서만 한다.

## 절차

### 1. 상태 목록 만들기 (대조의 분모)
대조할 **상태 × 폭** 목록을 먼저 고정한다. 목록이 곧 분모라서, 빠진 상태는 "차이 없음"이 아니라 "안 봤음"이다.

- 상태: 사용자가 실제로 마주치는 화면 상태(빈 목록 / 항목 선택 / 펼침 / 오류 / 권한 없음 등). 목업에 있는 상태를 우선 다 넣는다.
- 폭: 제품이 실제로 지원하는 대표 폭 2개 이상(예: 1440 · 900). 반응형 경계가 있으면 그 양쪽.
- 상태마다 **스타일 짝**을 몇 개 둔다: 같은 요소를 가리키는 목업 쪽 선택자와 앱 쪽 선택자, 비교할 CSS 속성
  (font-size·font-weight·color·padding·gap·width 등). 눈으로 애매한 크기·굵기 차이를 숫자로 확인하기 위해서다.
- 형식 예: `references/states.example.json`.

### 2. 캡처
- 목업과 앱을 **같은 상태로 만든 뒤** 같은 폭·같은 배율로 찍는다. 이름은 `<상태>-<폭>.png` 로 양쪽을 똑같이 맞춘다.
- 스타일 짝은 `getComputedStyle` 값으로 JSON 에 함께 남긴다.
- 도구: `scripts/capture.mjs`(Playwright). 목업·앱 각각 한 번씩 돌린다.
  ```bash
  node ~/.agents/skills/mockup-screenshot-diff/scripts/capture.mjs states.json --side mockup --out shots/mockup
  node ~/.agents/skills/mockup-screenshot-diff/scripts/capture.mjs states.json --side app    --out shots/app
  ```
- 앱을 띄우기 위해 저장 데이터·계정·외부 서비스를 바꾸지 않는다. 읽기 전용 상태 전환(탭·펼침·스크롤)만 쓴다.
  상태를 만들 수 없으면 그 상태는 **미캡처**로 남긴다.

### 3. 나란히 보기
```bash
python3 ~/.agents/skills/mockup-screenshot-diff/scripts/pair_sheet.py shots/mockup shots/app --out shots/compare
```
상태마다 `목업 | 앱` 비교 이미지와, 스타일 짝의 값 차이 표(`style-diff.md`)가 나온다. 비교 이미지를 직접 열어 본다.
숫자만 보고 판단하지 않는다 — 배치·위계·누락은 이미지에서만 보인다.

### 4. 차이 분류 (모든 차이에 하나씩)

| 분류 | 뜻 | 처리 |
|---|---|---|
| **구현 누락·불일치** | 목업에 있는 요소·배치·문구·스타일이 앱에 없거나 다름 | 에이전트가 고친다(범위 안이면) |
| **목업 전용** | 위 「목업 전용 장치」에 해당. 제품에 들어오면 안 되는 것 | 유지(앱에 가져오지 않음). 목록에 이유와 함께 남긴다 |
| **범위 밖·기존 제약** | 공용 컴포넌트 기본 크기, 라이브러리 버튼 패딩 등 이 작업이 바꿀 수 없는 것 | 남은 차이로 기록, 필요하면 후속 작업 제안 |
| **애매함** | 목업 의도를 확정할 수 없음(새 상태, 데이터 차이, 목업끼리 모순, 토큰에 없는 값) | **개발자에게 질문** |

분류할 때 지키는 것:
- 차이를 발견했다고 다 고치지 않는다. 분류가 먼저다.
- "목업이라서" 생긴 차이로 넘기려면 그것이 왜 목업 전용인지 한 줄로 쓸 수 있어야 한다. 못 쓰면 애매함이다.
- 데이터 양·문구 길이 차이(예시 데이터 3건 vs 실제 200건)는 배치 차이로 오인하기 쉽다. 같은 데이터로 다시 찍을 수 없으면 애매함으로 둔다.

### 5. 스스로 해소 / 질문
- **해소:** 구현 누락·불일치를 고친다. 고친 뒤 **같은 상태를 다시 찍어** 그 차이가 사라졌는지 확인한다. 확인 못 하면 "수정했으나 미확인"이다.
- **질문:** 애매한 것만 묶어서 묻는다. 질문마다 비교 이미지(또는 잘라낸 부분), 두 해석, 내 제안을 붙인다.
  묻기 전에 같은 성격의 항목은 한 질문으로 합친다 — 모든 픽셀 차이를 묻지 않는다.
- 차이가 많으면 화면 영역별로 후속 작업 묶음(예: 상단 맥락 막대 / 목록 / 상세 패널)으로 나눠 제안한다.

### 6. 결과 기록 — 「대조 결과(남은 차이)」
작업 기록(구현 노트·PR 본문 등)에 아래를 남긴다.

```markdown
## 대조 결과(남은 차이)
- 범위: 상태 N개 × 폭 [1440, 900] · 캡처 도구/명령 · 미캡처 상태: …
- 해소: <차이> → <무엇을 바꿨나> (재캡처 확인: <상태-폭>)
- 남은 차이(범위 밖·기존 제약): <차이> — <이유> (예: 공용 버튼 기본 크기 12.25px vs 목업 14px, 이 작업 밖)
- 목업 전용(유지): <안내 띠·화면 ID·예시 데이터 …>
- 질문 대기: <질문 요약> → <누구에게>
```

## Do not
- 목업 전용 장치를 제품에 옮기기
- 목업 색·간격을 토큰 없이 하드코딩하기, 전역 스타일을 바꿔 한 화면을 맞추기
- 한 장의 캡처로 "모든 상태 일치"라고 말하기 — 상태 목록 밖은 안 본 것이다
- 재캡처 없이 "해결"이라고 보고하기
- 애매한 차이를 에이전트가 임의로 확정하기
- 캡처를 위해 저장·제출·결제·발송 같은 영속 동작을 실행하기
