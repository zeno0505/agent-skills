# 작성자 말투 맞추기

사람 이름으로 나가는 글(블로그, 슬랙 글·답글, 팀 공유 글)의 목소리를 **작성자 본인 말투**로 맞추는 기준이다. `weekly-lesson-draft`, `slack-reply-draft` 같은 초안 스킬은 말투 규칙을 직접 들고 있지 않고 이 스킬을 불러 쓴다.

**적용 대상이 아닌 것**: 에이전트가 작성자에게 직접 하는 답장. 에이전트 자신의 말투(예: 비서 말투, 반말 캐릭터)는 별도 규칙이며, 작성자 글에 섞지 않는다.

## 왜 별도 스킬인가
글 종류마다 관례 문체가 있다(블로그는 평서 `~다` 서술체, 보고서는 개조식). 관례대로 쓰면 문장은 매끄러워도 작성자에게 「내가 쓴 것 같지 않다」는 피드백을 받기 쉽다. 기준은 관례가 아니라 **작성자가 평소 채팅에서 실제로 쓰는 말투**다. 이 기준을 채널별 초안 스킬마다 복사하면 서로 어긋나므로 한곳에 둔다.

## 1) 말투 가이드 만들기 (작성자 원문에서)
작성자별 가이드는 **개인 설정**(로컬 스킬·메모 등)에 두고, 이 공개 스킬에는 틀만 둔다.

1. **원문 모으기**: 작성자가 채팅·회고 답·슬랙에 직접 쓴 문장 10개 이상. 에이전트가 다듬은 문장, 남이 쓴 인용은 뺀다. 새 원문이 쌓이면 가이드를 다시 확인한다.
2. **관찰 항목을 표로 뽑기**:
   | 항목 | 볼 것 |
   |---|---|
   | 문장 끝 | 평서/존댓말(`~습니다`)/요체(`~해요`) 비율, 판단을 말할 때의 끝(`~라고 봅니다`, `~것 같습니다`) |
   | 전환 | 문장 중간에 쓰는 `~인데요,` `~는데,` 같은 이음 |
   | 연결어 | 문장 첫머리 접속어(`특히`, `따라서`, `다만` …)와 쉼표 습관 |
   | 1인칭 | `저/제` vs `나/내` |
   | 문장 길이 | 한 문장에 절을 몇 개 잇는지 |
   | 주장 강도 | 단정 vs 자기 판단 표지 |
3. **규칙으로 옮기기**: 관찰을 「기본값 / 가끔 / 금지」 세 칸으로 정리한다. 빈도가 낮은 습관은 「가끔(글당 1~2번)」으로 둬서 남발을 막는다.
4. **✗/○ 쌍 만들기**: 같은 내용을 관례 문체(✗)와 작성자 말투(○)로 나란히 쓴 쌍을 3개 이상 둔다. 원문 문장을 그대로 공개 저장소에 옮기지는 않는다.
5. **오탈자 원칙**: 원문의 띄어쓰기·오타는 옮기지 않는다. 말투만 살린다.
6. **작성자 확인**: 가이드 초안을 작성자에게 보여 주고 확정한다.

## 2) 기본값 예시 (작성자가 존댓말 채팅을 쓰는 경우)
- **문장 끝**: `~합니다 / ~습니다 / ~입니다`. 판단은 `~라고 봅니다`, `~라고 생각합니다`. 결정은 `~하기로 했습니다`. 전환에 `~인데요,`를 가끔.
- **1인칭**: `저/제`. `나/내`와 섞지 않는다.
- **문장 길이**: 한 문장에 절 2~3개, 한 문단 2~4문장.
- **주장 강도**: 판단은 `~라고 봅니다`로 자기 판단임을 드러내고, 한 일은 `~했습니다`로 담백하게.
- **금지**: 작성자 말투와 다른 서술체, 비서 봇 말투(「~할게」「~해 둘게」), 마케팅·튜토리얼 톤(「~해 보세요!」).

✗/○ 쌍 (같은 내용, 문체만 다름):
- ✗ 「따져 보니 내 작업 흐름에 이미 비슷한 장치가 있었다.」
- ○ 「그런데 따져 보니 제 작업 흐름에 이미 비슷한 장치가 있었습니다.」
- ✗ 「위험도 분류가 하려는 일을 이 정책이 이미 담고 있었다.」
- ○ 「위험도 분류가 하려는 일을 이 정책이 어느 정도 이미 담고 있었다고 봅니다.」
- ✗ 「이번 변경으로 검증 여부를 기계적으로 판별할 수 있게 됐다.」
- ○ 「이로 인해 검증 여부를 기계적으로 판별할 수 있게 되었습니다.」

## 3) 채널 노트
- **블로그**: 제목·소제목은 헤드라인이라 평서형(`~다`)을 그대로 둬도 된다. 본문만 작성자 말투.
- **슬랙**: 블로그보다 문장을 짧게(절 1~2개), 불릿을 적극적으로. 같은 채널·스레드에서 작성자가 최근에 쓴 글의 어미·호칭·목록 습관이 가이드와 다르면 **그 자리의 실제 글이 우선**이다. 접두어·레이어 같은 구조 규칙은 `slack-reply-draft`가 맡는다.
- **비개발 청중(QA·운영 등)**: 청중의 관점(무엇을 확인하면 되는지, 어떤 상황에서 문제가 되는지)으로 쓰고, 구현·UI 세부와 전문 용어는 최소로 줄이거나 풀어 쓴다.

## 4) 기계 점검 (마무리 전)
1. 존댓말 가이드라면, 제목·소제목·그림 줄·코드 블록·인용을 뺀 본문에서 `다.`로 끝나는 서술문을 훑는다: `rg -o '[^ ]+다\.' <초안 파일>`. 남은 것은 가이드대로 고친다.
2. 가이드의 「금지」 목록(예: `할게`, `해 둘게`, 섞인 1인칭)을 같은 방식으로 찾는다.
3. 기계 점검은 예비다. 「작성자가 쓴 것 같은지」는 작성자 리뷰가 최종 게이트다.
