# 최소 설계 검토

## Overview

현재 설계와 코드 구조에 군더더기가 있는지, 다른 접근이 더 작게 끝나는지를
**서브에이전트에게 반박시켜** 확인합니다.

핵심 원리: **대안을 만드는 쪽과 판정하는 쪽을 분리합니다.**
내 안을 내가 검토하면 검토가 아니라 방어가 됩니다.

## When to Use

명시 호출 전용입니다. 사용자가 부르지 않으면 이 스킬은 동작하지 않습니다.

- 설계를 확정하기 직전
- 큰 리팩터를 시작하기 직전
- 파일 수나 계층이 늘어나는 것이 마음에 걸릴 때

**쓰지 말 것:** 변경분 리뷰(`/code-review`, `/simplify`), 버그 원인 추적
(`superpowers:systematic-debugging`), 사용자가 이미 확정한 정책의 재론.

## 사다리

포니테일(MIT, github.com/dietrichgebert/ponytail)의 7단계를 판단 기준으로 씁니다.
먼저 걸리는 단에서 멈춥니다.

1. 존재할 필요가 있나 (YAGNI). 추측성 필요면 뺍니다.
2. 이 코드베이스에 이미 있나. 있으면 재사용합니다.
3. 표준 라이브러리가 하나. 하면 그걸 씁니다.
4. 플랫폼 기본 기능이 덮나. 덮으면 그걸 씁니다.
5. 이미 설치된 의존성이 푸나. 풀면 그걸 씁니다. 몇 줄이면 될 일에 새 의존성을 넣지 않습니다.
6. 한 줄로 되나. 되면 한 줄입니다.
7. 그제서야, 동작하는 최소한.

사다리는 해답을 줄이지 이해를 줄이지 않습니다. 대상 흐름을 끝까지 읽은 뒤에 탑니다.
이해를 건너뛰고 나온 짧은 diff 가 가장 위험한 결과물입니다.

## 절차

1. **대상 확정** — 무엇을 검토할지 한 줄로 적고 사용자에게 확인받습니다.
2. **반박자 파견** — 아래 프롬프트를 채워 보냅니다. 파견 방법은 런타임에 따라 다릅니다.
3. **근거 검증** — 서브에이전트 결론을 그대로 옮기지 않습니다. 각 항목이 짚은
   파일을 직접 열어 실재하는지 확인합니다. 확인하지 못한 항목은 미확인으로 표시합니다.
4. **보고와 게이트** — 표로 옮기고 채택 게이트를 겁니다.

## 런타임별 파견 방법

무엇으로 띄우든 **반박자는 별도 컨텍스트에서 돌아야 합니다.** 같은 세션이 스스로
반박하면 검토가 아니라 방어가 됩니다. 이 스킬의 전부가 그 분리에 걸려 있습니다.

| 런타임 | 파견 방법 |
| --- | --- |
| Claude Code | `Agent(subagent_type: "fork")` — 세션 맥락을 물려받되 결론은 물려받지 않습니다 |
| Codex CLI | `codex exec -s read-only -C <저장소 루트> "<아래 프롬프트>"` — 새 프로세스라 맥락이 비어 있으므로, 프롬프트의 `현재 안` 한 문단에 판단 근거를 모두 담습니다 |
| 그 외 | 새 세션·새 프로세스로 띄울 수 있으면 무엇이든 됩니다. 같은 세션에서 자문자답하지 마십시오 |

Codex 로 파견할 때 `-s read-only` 는 선택이 아닙니다. "코드를 수정하지 마십시오" 라는
프롬프트 규칙을 샌드박스가 대신 강제해 줍니다.

## 반박 프롬프트

```
당신은 이 세션의 맥락을 물려받았지만 지금까지의 결론을 지지하지 않습니다.
현재 설계를 반박하는 것이 당신의 일입니다.

검토 대상: <경로 또는 설계 요약>
현재 안: <한 문단>

규칙:
- 앞선 결론을 믿지 말고 대상 파일을 직접 다시 읽으십시오.
- 코드를 수정하지 마십시오. 읽기와 보고만 합니다.
- 사다리 7단을 적용하되 "더 나은 패턴" 같은 추상적 지적은 금지입니다.
  모든 지적은 파일과 줄을 짚어야 합니다.
- 스택 대안에는 새로 지는 비용(의존성·학습·마이그레이션)을 반드시 함께 적습니다.
  비용을 적지 않은 대안은 제출하지 마십시오.
- 없는 항목은 "없음"이라고 적습니다. 채우려고 지어내지 마십시오.

아래 형식으로만 답하십시오.
<출력 형식>
```

## 출력 형식

```
1. 군더더기
   <파일>:<줄> <잘라낼 것>. <대체물>.
2. 스택 대안
   현재 <X> → <Y>. 사라지는 것: <...>. 새로 지는 비용: <...>.
3. 손대면 안 되는 것
   <입력 검증·에러 처리·보안·접근성·사용자가 명시 요구한 것 중 해당 항목>
4. 판정
   net -<N>줄 또는 -<N>파일   /   Lean already.
```

## 채택 게이트

대안을 받아들이려면 셋이 **모두** 있어야 합니다.

1. 대안이 실재하는 파일과 줄을 짚는다
2. 내가 그 파일을 직접 열어 근거를 확인했다
3. 사용자가 승인했다

하나라도 없으면 한 줄 사유로 기각하고 현재 안을 유지합니다.
기각한 항목도 보고에 남깁니다.

## 보고 형식

| 항목 | 현재 안 | 대안 | 근거 확인 | 처리 |
| --- | --- | --- | --- | --- |

처리는 채택 / 기각(사유) / 사용자 판단 셋 중 하나입니다.

## Red Flags — 멈추고 다시 합니다

- 서브에이전트 보고를 확인 없이 그대로 옮겼다 → 3단계를 건너뛴 것입니다
- "더 좋은 패턴이니까" 로 채택했다 → 게이트 1 위반입니다
- 사용자 승인 없이 코드를 고치기 시작했다 → 게이트 3 위반입니다
- 잘라낼 게 없는데 억지 항목을 만들었다 → `Lean already.` 가 정답입니다
- 입력 검증·에러 처리·보안·접근성을 잘라냈다 → 사다리의 대상이 아닙니다
