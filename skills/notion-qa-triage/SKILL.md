# Notion QA Triage

노션 프로젝트의 열린 QA를 근거와 함께 네 가지로 분류하고 다음 처리 행동을 정한다. 원인 미확정을 수정 방향 미확정과 혼동하지 않는다.

## 입력과 범위

- 필수: 노션 프로젝트 URL.
- 선택: 대상 플랫폼·담당자·기간, 저장 위치, 연결된 저장소, 구현/태스크 등록까지 진행할지.
- 기본은 프로젝트에 연결된 열린 QA 전체의 조회·분류·처리 제안이다. 완료/닫힘 항목과 상위 그룹은 집계에서 분리한다.
- 분류 요청만으로 코드 변경, DAG 등록, 노션 상태 변경, 댓글 작성, Slack 발송을 시작하지 않는다. 세션에서 이미 승인된 후속 작업은 해당 범위 안에서 이어간다.

## 자료 수집

1. 노션 MCP로 프로젝트를 fetch하고 QA 데이터베이스·데이터 소스·saved view를 찾는다. 데이터 소스 schema와 도구 접근 조건을 확인한 뒤 조회한다. 인증 실패는 그대로 보고하며 빈 목록으로 해석하지 않는다.
2. 실제 view의 프로젝트 relation·QA 유형 필터를 확인한다. 복제 템플릿의 다른 프로젝트 필터를 그대로 사용하지 않는다. 프로젝트의 QA saved view를 사용하거나 schema에 맞는 명시적 필터로 조회하고, 모든 페이지를 끝까지 가져온다.
3. 이슈의 본문, As-is/To-be, 재현 경로·환경, 전체 댓글을 읽는다. 댓글의 추가 요구사항을 별도 쟁점으로 분리하고, 같은 이슈가 여러 view에 있으면 URL/ID로 중복 제거한다.
4. 첨부는 현재 도구가 제공하는 원본 URL·references를 통해 열람을 시도한다. 노션 MCP는 첨부 이미지·영상의 내용을 돌려주지 않고 링크만 주는 경우가 많다. 이미지·영상은 파일 링크만 받았다고 읽었다고 하지 않는다. 가능하면 이미지 확인과 영상의 관련 구간/프레임 확인을 수행한다. 다운로드·권한·재생 실패 및 확인한 구간을 기록한다.
5. 기존 사용자 합의와 프로젝트 요구사항을 대조한다. 다른 환경에서 발견한 오류를 이 이슈의 원인으로 단정하지 않는다. 원인 조사가 필요한 경우에만 관련 코드/API/배포 상태를 확인한다.

## 분류 기준

각 쟁점에 주 분류 하나를 붙인다. 한 티켓에 다른 성격의 쟁점이 있으면 행을 나눈다. 네 분류를 모두 채우기 위해 근거 없는 설계 결정을 만들지 않는다.

| 주 분류 | 판정 | 다음 처리 |
|---|---|---|
| 기획·디자인 확인 필요 | 검사 범위·가입 정책·문구·위치·간격 등 기대 동작 자체가 미합의 | 기존 합의와 미결정 질문을 분리하고, 결정할 사람과 선택지를 명시. 결정 후 구현/회귀 확인 |
| 설계적으로 고민 필요 | 갱신 시점·선택 항목 유지·상태 전이·선행 조건/API 연동 등 구현 전략이 미정 | 결정할 전략과 원인 조사 항목을 명시. 근거 있는 대안·차이를 제시하고 영향/검증 조건을 정함 |
| 수정 방향 명확 | 기존 요구사항과 어긋나는 동작이며 기대 결과와 최소 수정 방향이 명확 | 재현 → 코드에서 누락 지점 확인 → 최소 수정 → 회귀 검증. 근거 없는 원인·파일명은 확정하지 않음 |
| 사용자 직접 확인 필요 | 핵심 현상이 첨부에만 있고 열람 실패·재현 정보 부족으로 현상을 특정할 수 없음 | 사용자가 확인할 정확한 화면·조작·질문을 적음. 새 정보를 받으면 다시 분류 |

적용 시 주의 (실제 분류에서 나온 예시):
- 수정한 금칙어가 항목 이동 후에만 사라진다는 댓글만으로 Enter 즉시 재검사를 요구하지 않는다. 기존 갱신 정책을 먼저 확인하고, 미정이면 검사 시점과 선택 유지 전략을 검토한다.
- 가입 불가 이슈는 계약/인증 등 선행 조건과 실패 상태 전달을 조사한다. 결제 화면을 바로 열어 선행 조건을 우회하는 수정 방향을 제시하지 않는다. 이미지 미열람이어도 텍스트로 조사 방향이 정해지면 자동으로 사용자 직접 확인에 넣지 않는다.
- 시리즈에서 시작한 작성이 시리즈를 잃고 일반 작성의 선택은 정상이라면, 시리즈 문맥 전달·저장 유지가 수정 방향이다. 실제 누락 지점은 코드 확인 전까지 가설이다.
- 어떤 필드(예: 제목)를 검사에서 빼기로 한 합의는 다른 필드(예: 태그)까지 빼기로 한 합의가 아니다. 새로운 검사 범위는 정책 확인으로 분리한다.
- 사용자가 첨부의 내용을 설명해 핵심 현상이 특정되면 직접 확인 분류에 계속 두지 않는다. 설명을 근거로 재분류하고 다음 조사를 진행한다.

## 출력과 후속 처리

출력은 한국어로 작성한다.

1. 조회한 범위·열린 이슈 수·첨부 열람 한계를 짧게 설명한다.
2. `분류 | 이슈(원본 링크) | 근거·미확정 사항 | 다음 처리·검증 조건` 표를 작성한다. 관측 사실, 사용자 합의, 원인 가설을 구분한다.
3. 바로 수정할 항목, 결정 후 진행할 항목, 조사할 항목, 사용자 확인 질문을 우선순위 순으로 정리한다. 과거 환경이나 오래된 이슈는 현재 재현 여부를 확인할 대상으로 표시한다.

태스크 등록/구현까지 요청됐으면 기존 태스크와 중복 및 현재 승인을 확인하고 필요한 항목만 이어간다. DAG가 있으면 [`read-dag-stack`](../read-dag-stack), [`show-dag-stack`](../show-dag-stack), [`append-dag-stack`](../append-dag-stack), [`set-dag-stack`](../set-dag-stack), [`run-dag-stack`](../run-dag-stack)을 해당 단계에서 사용한다. 화면 수정 전 저장소의 라우트 소유 앱·컴포넌트 소비자를 확인한다. 각 태스크에는 원본 이슈 링크, 확정 요구사항, 미결정 사항/의존성, 재현 및 검증 조건을 남긴다. 결정 대기 항목을 완료로 처리하거나 재현 실패만으로 노션 이슈를 닫지 않는다.
